# SF-001: исправления приёмки

База изменений: `dbfa3d981064157ceffd3e8e4adc960a7cfb56ef`.
Удалённая БД, миграции и production в рамках этого изменения не обновляются.

## Что исправлено

- **SF-A01:** ИИ API проверяет Bearer JWT через Supabase Auth `getUser(jwt)` с публичным ключом; клиент передаёт текущий access token. Неподтверждённый запрос не достигает Gemini. Ограничены размер сообщения/тела, история, время запроса и произвольные поля профиля. Добавлены 6 обращений в минуту на пользователя и один одновременный запрос **на экземпляр процесса**.
- **SF-A02:** сообщения удаляются только после успешного сохранения сводки с возвращённым идентификатором. Повтор того же набора сообщений использует детерминированный UUID и существующий первичный ключ, без новой миграции. Ошибки сохранения/удаления отражаются в failed и HTTP 500. Это не межтабличная транзакция; параллельные перекрывающиеся пакеты требуют отдельной проверки.
- **SF-A03:** текст продуктов, корзины, журнала, рецептов, подсказок и тостов экранируется/выводится через textContent. Подстановка emoji в JS-обработчик изображения заменена безопасным data-атрибутом и статичным обработчиком.
- **SF-A04:** ветка основана на актуальном клиенте с create_household/join_household RPC. Сбой чтения членства не воспринимается как отсутствие семьи. Production остаётся на старой версии до отдельно согласованного выпуска.
- **SF-A05:** восстановление использует window.history, отображает ошибку и разблокирует форму; экран входа скрывается после загрузки данных.
- **SF-A06:** build отклоняет отсутствующие/некорректные обязательные настройки и непубличный ключ до очистки dist; значения вставляются целыми JS-литералами с защитой от закрытия script.
- **SF-A07:** оба cron закрыты при отсутствующем CRON_SECRET. Сравнение заголовка выполняется через timingSafeEqual.
- **SF-A08:** Open Food Facts proxy проверяет метод, timeout и HTTP-статус upstream; ошибки не кэшируются как HTTP 200.

## Проверка

`npm test` запускает node:test без установки зависимостей и внешней сети. Обработчики выполняются с заглушками Auth, Gemini, БД и уведомлений. Пароли, ключи и данные production не нужны.

Для настоящей сборки задайте SUPABASE_URL и SUPABASE_ANON_KEY своего тестового проекта, затем `npm run build`. Обычный node build.js не загружает .env.local автоматически; переменные должны быть переданы процессу. Vercel передаёт их из настроек соответствующего target. Шаблон — `.env.example`; значения не коммитить. `dist` раздаётся статическим сервером; для API нужен Vercel runtime. Пустая конфигурация теперь намеренно блокирует preview/build.

## Второй проход: ввод, сохранение и камера

Находки отдельного UX-аудита старого production перепроверены на текущем коде. Исправлено:

- Редактирование продукта ждёт подтверждённого UPDATE. При отказе/нуле обновлённых строк локальный продукт и отделение не меняются; форма остаётся открытой с ошибкой. Повторный клик во время записи игнорируется, поздний ответ не возвращает пользователя на уже закрытую карточку.
- Нулевое/отрицательное/нечисловое количество отклоняется при редактировании и подтверждении распознанного продукта. Дробные положительные значения поддерживаются.
- Сохранение профиля проверяет реальный результат INSERT/UPDATE, валидирует возраст и положительные числовые поля; дробный вес и рост не блокируются шагом 1.
- Текущий вес при редактировании записывается отдельным замером за текущую дату, не переписывая стартовый вес. Обновление только веса не стирает шею, грудь и другие замеры. Неизменённый вес не создаёт фиктивный замер.
- После частичного успеха (профиль создан, начальный замер не записан) форма сохраняет ID. Повтор продолжает работу с тем же профилем, а не создаёт дубликат.
- Выход из Vision останавливает media tracks и отвязывает preview. Поздний getUserMedia освобождается сразу; поздняя загрузка детектора не перезапускает таймер.
- Ошибка модели/фото больше не подставляет случайный продукт: название очищается, предлагается ручной ввод.

После второго прохода набор содержал 52 проверки в `tests/acceptance.test.cjs` и `tests/ui-reliability.test.cjs`. Камера, Auth, база, модель и внешние сервисы в этих проверках заменены заглушками. Это проверка логики, не физического устройства или настоящего браузера.

## Третий проход: добавление, списание и покупки

- Ручной ввод, чеклист и подтверждение Vision добавляют данные в локальные списки только после подтверждённого INSERT. Чеклист записывается одним запросом. Кнопка заблокирована до завершения; ошибка сохраняет форму.
- Неизменённая повторная попытка в той же вкладке сохраняет UUID: после потерянного ответа конфликт первичного ключа проверяется чтением всех ожидаемых строк в текущей семье. Существующие строки не перезаписываются. Локальный список строится из ответа базы. После перезагрузки нужно сверить загруженный список; новая отправка формы — новая операция.
- Добавление недостающего в покупки также ждёт подтверждения и сохраняет ID неудачной попытки в текущей вкладке. Одновременные клики по одному названию используют один запрос; проверка названия между устройствами пока не атомарна.
- «Использовать»/«Выбросить» ждут DELETE с возвращённым ID. Отказ/ноль строк не меняют локальный продукт и счётчики. После подтверждённого удаления ошибки журнала/статистики явно отображаются как частичное списание. Локальная блокировка защищает от одновременного повторного действия в этой вкладке.
- Списание для блюда выполняется последовательно по сохранённым объектам. При частичном отказе показывается число подтверждённых списаний, список ингредиентов перестраивается без уже списанных. Название блюда не хранится как отдельная запись; сообщение больше не утверждает, что блюдо сохранено.
- Перенос покупки сначала подтверждает продукт, затем удаляет покупку. UUID назначения равен UUID покупки в другой таблице, поэтому повтор, в том числе после перезагрузки, читает тот же продукт. Если удаление покупки не подтверждено, она остаётся в интерфейсе. Ждать нужно оба запроса; полной транзакции здесь нет.
- Виджет ждёт перенос и очищает только подтверждённые отметки. Ошибки оставляют отметки для следующей попытки; перерисовка в ходе синхронизации не запускает бесконечный цикл повторов. Параллельная синхронизация блокируется.

Текущий набор: **72 проверки**, включая `tests/persistence.test.cjs`. Добавлены моделируемые отказы, ноль строк, потерянный ответ после записи, повтор после перезагрузки объекта покупки, двойной клик, частичное списание и ошибки виджета. `npm run build` с синтетическими публичными настройками и `git diff --check` также проходят.

**Остаётся блокером:** продукт, журнал и статистика не объединены в серверную транзакцию. Потеря связи после DELETE/ошибка вторичной записи может оставить неполный журнал или счётчики. Несколько устройств могут перезаписать счётчики food_stats. Между созданием продукта и удалением покупки остаётся промежуточное состояние; если в нём списать созданный продукт, повтор переноса может создать его снова. Для гарантии между устройствами нужны серверные операции с идемпотентным ID и транзакцией, отдельно проверенные на тестовой БД. Клиентские подтверждения не заменяют их; production и схема БД в этом PR не менялись.

## Общее ограничение ИИ: решение для следующего этапа

Предпочтительный вариант без нового внешнего сервиса — общий атомарный счётчик в существующем Supabase. Здесь он **не создавался и не включался**, поскольку изменения рабочей схемы запрещены текущими условиями.

Требования к реализации:

1. Закрытое хранилище квоты: клиент не может удалять, менять или обнулять счётчики; отдельные окна на пользователя и всё приложение.
2. Одна серверная операция резервирует запрос атомарно с фиксированным порядком блокировок. Идентификатор пользователя берётся из проверенной Auth-сессии, лимиты задаёт сервер.
3. Несколько экземпляров API обращаются к одному счётчику перед Gemini. При недоступности счётчика ответ 503; без автоматического перехода к локальному лимиту. При превышении — 429 и Retry-After.
4. Проверки конкурентных запросов с двух процессов, границ окна, отсутствия доступа к чужой квоте и отказа хранилища должны пройти на отдельной тестовой БД.
5. Денежный лимит провайдера настраивается отдельно: число запросов не является точным бюджетом. Конкретные квоты и схема готовятся к отдельному согласованному включению.

## Что остаётся до закрытия приёмки

1. **Общий лимит расходов ИИ.** In-memory guard не является глобальной квотой между экземплярами Vercel и сбрасывается при холодном старте. До публичного запуска нужен общий счётчик/лимит на стороне инфраструктуры и лимит бюджета провайдера. Это потребует отдельной конфигурации; новая БД/платные сервисы здесь не создаются.
2. Полный браузерный проход, восстановление пароля и сценарии двух пользователей/семей на изолированных данных. Локальные VM-проверки не заменяют браузер и RLS end-to-end.
3. Регистрация webhook, реальная доставка Telegram/Web Push, cron и ответы Gemini не проверяются отправкой в этом PR.
4. Установка зависимостей, lock-файл, CI, корректность рекомендаций по питанию и тексты privacy остаются отдельными задачами.
5. После принятия изменений — отдельно согласованный merge/release. Не откатывать RLS ради старого клиента. Для старой версии код создания/вступления в семью несовместим с текущими каталогами БД.

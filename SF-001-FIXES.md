# SF-001: исправления приёмки

База изменений: `dbfa3d981064157ceffd3e8e4adc960a7cfb56ef`.
Удалённая БД, миграции и production в рамках этого изменения не обновляются.

## Что исправлено

- **SF-A01:** ИИ API проверяет Bearer JWT через Supabase Auth `getUser(jwt)` с публичным ключом; клиент передаёт текущий access token. Неподтверждённый запрос не достигает Gemini. Ограничены размер сообщения/тела, история, время запроса и произвольные поля профиля. Добавлены 6 обращений в минуту на пользователя и один одновременный запрос **на экземпляр процесса**.
- **SF-A02:** сообщения удаляются только после успешного сохранения сводки с возвращённым идентификатором. Повтор того же набора сообщений использует детерминированный UUID и существующий первичный ключ, без новой миграции. Ошибки сохранения/удаления отражаются в failed и HTTP 500. Это не межтабличная транзакция; параллельные перекрывающиеся пакеты требуют отдельной проверки.
- **SF-A03:** текст продуктов, корзины, журнала, рецептов, подсказок и тостов экранируется/выводится через textContent. Подстановка emoji в JS-обработчик изображения заменена безопасным data-атрибутом и статичным обработчиком.
- **SF-A04:** ветка основана на актуальном клиенте с create_household/join_household RPC. Сбой чтения членства не воспринимается как отсутствие семьи. Production остаётся на старой версии до отдельно согласованного выпуска.
- **SF-A05:** восстановление использует window.history, отображает ошибку и разблокирует форму; экран входа скрывается после загрузки данных.
- **SF-A06:** build отклоняет отсутствующие/некорректные обязательные настройки и непубличный ключ до очистки dist; значения вставляются целыми JS-литералами с защитой от закрытия script.
- **SF-A07:** оба cron закрыты при отсутствующем CRON_SECRET. Сравнение заголовка выполняется через timingSafeEqual.
- **SF-A08:** Open Food Facts proxy проверяет метод, timeout и HTTP-статус upstream; ошибки не кэшируются как HTTP 200.

## Проверка

`npm test` запускает node:test без установки зависимостей и внешней сети. Обработчики выполняются с заглушками Auth, Gemini, БД и уведомлений. Пароли, ключи и данные production не нужны.

Для настоящей сборки задайте SUPABASE_URL и SUPABASE_ANON_KEY своего тестового проекта, затем `npm run build`. Обычный node build.js не загружает .env.local автоматически; переменные должны быть переданы процессу. Vercel передаёт их из настроек соответствующего target. Шаблон — `.env.example`; значения не коммитить. `dist` раздаётся статическим сервером; для API нужен Vercel runtime. Пустая конфигурация теперь намеренно блокирует preview/build.

## Что остаётся до закрытия приёмки

1. **Общий лимит расходов ИИ.** In-memory guard не является глобальной квотой между экземплярами Vercel и сбрасывается при холодном старте. До публичного запуска нужен общий счётчик/лимит на стороне инфраструктуры и лимит бюджета провайдера. Это потребует отдельной конфигурации; новая БД/платные сервисы здесь не создаются.
2. Полный браузерный проход, восстановление пароля и сценарии двух пользователей/семей на изолированных данных. Локальные VM-проверки не заменяют браузер и RLS end-to-end.
3. Регистрация webhook, реальная доставка Telegram/Web Push, cron и ответы Gemini не проверяются отправкой в этом PR.
4. Установка зависимостей, lock-файл, CI, корректность рекомендаций по питанию и тексты privacy остаются отдельными задачами.
5. После принятия изменений — отдельно согласованный merge/release. Не откатывать RLS ради старого клиента. Для старой версии код создания/вступления в семью несовместим с текущими каталогами БД.

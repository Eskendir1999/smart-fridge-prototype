# Ужин и «Мои данные»: дополнение для приёмки

3 ноября 2026. Продолжение PR №12. Только подготовка: пользователь оставил выпуск за чатом
«SF — Надёжное сохранение и остатки», `01a19c2c-63f3-7e33-ba82-077718d2bb1f`.
Код и SQL production не менялись. Все существующие gates остаются выключенными.

## Найденная зависимость

В тексте подготовленного Stage3 «Мои данные» удаление профиля затрагивает профиль и замеры.
В новой dinner_operations остаётся исходный запрос с profile ID, режимом и исключениями.
Применение одного Stage3 не очищает эту новую производную копию. Удалять квитанцию целиком
нельзя: после потерянного ответа исчезнет защита от повторного списания. SQL этого дополнения
не подменяет сам Stage3 и не объявляет его выпускную приёмку выполненной.

## Подготовленный мост

`review/dinner-my-data.sql` — отдельный review-кандидат, **не автоматическая migration**.
Его нет в списке продуктовых миграций и helper не применяет его без явной команды теста.
Требует dinner schema и подтверждённую owner-колонку; её отсутствие даёт отказ.
Не создаёт владельцев, не присваивает legacy-профили, не меняет gates или существующие RLS.

- `sf_dinner_my_data()` — read-only RPC для экспорта собственных dinner-действий. Постоянный
  аккаунт проверяется по auth.users, actor не принимается с клиента. Возвращаются собственные
  операции, их личный контекст/блюда, минимальные изменения количества и собственные события.
  Raw before/after stock-снимки и метаданные создателя чужой общей партии не возвращаются.
  Экспорт доступен и после выхода из прежней семьи; чужие операции не добавляются.
  Лимит сериализованного результата — 5 MiB. Это дополнение к полному экспорту аккаунта.
- AFTER DELETE trigger собственного подтверждённого профиля очищает **весь payload** связанных
  dinner-квитанций его владельца. Ставится profile_context_erased_at. Сохраняются ID квитанции,
  механические снимки партий для undo, счётчики и общий журнал запасов. Чужие операции и
  контекст других профилей не затрагиваются. Ошибка очистки откатывает и удаление профиля.
- dinner_requirements уже держит SHARE-блокировку профиля до commit. Удаление ждёт выполняющийся
  расход, затем trigger очищает и его только что сохранённую квитанцию. Новый расход с удалённым
  профилем отвергается. Общую household-блокировку в trigger добавлять нельзя: это меняло бы
  порядок блокировок и создавало бы риск взаимной блокировки.
- Очищенная квитанция не исполняется повторно. Старый запрос с личным payload получает отказ
  сравнения payload; `resolve` с прежним UUID и пустым body подтверждает сохранённый результат.
  Undo по собственной квитанции работает без повторного чтения удалённого профиля.

Публичная RPC SECURITY INVOKER; узкие definer-функции находятся в непубличной sf_private,
с пустым search_path и закрытым прямым доступом. Trigger не доступен для прямого вызова клиентом.

## Подключение к Stage3 ответственным за выпуск

1. Сначала принять ownership/MyData stage и его реальную схему. Не применять накопительный старый
   Stage3 поверх main вслепую: сохранить принятые Nutrition Stage2 и dinner-защиты.
2. После отдельного review подготовить deployment migration на основе этого SQL. Сам файл в
   review не запускать автоматически. Проверить constraints, grants, advisors и managed Auth.
3. При каждом чтении/скачивании Stage3 добавить свежий результат `sb.rpc('sf_dinner_my_data')`
   к JSON/CSV. Если любая часть чтения не подтверждена — не выдавать файл за полный экспорт.
   CSV должен сохранять защиту от формул. Не делать постоянный клиентский кэш снимка.
4. **До отправки** любого удаления личных данных вызвать
   `window.dispatchEvent(new Event('sf:personal-data-deleting'))`. Обработчик dinner очищает
   DOM/память и заменяет незавершённый личный запрос на opaque resolve. При потерянном ответе
   не восстанавливать прежние ограничения. После подтверждения обновить dinner snapshot.
   Начало удаления само по себе не списывает и не отменяет общий запас.
5. Удаление подтверждённого профиля через серверную Stage3-функцию или direct API запускает
   один и тот же trigger в той же транзакции. После неизвестного результата расход разрешается
   только через прежний UUID/resolve. Не удалять локальные ID и server receipts до сверки.

Сам экран Stage3, его архив и общая privacy-migration в этот PR не копируются. Контракт Stage3
прочитан в истории профильного чата; его ZIP не был получен и побайтовая интеграция не заявляется.
Новый мост проверяется отдельно на синтетических владельцах и локальной настоящей HTTP/SQL границе.

## Проверки и оставшиеся условия

**192/192 теста и 14 dinner HTTP групп PASS** (185 + 7 новых SQL; 11 + 3 новых HTTP).
Синтетическая сборка, JS syntax и diff check — PASS.

Новые SQL-проверки: только собственный экспорт, выход из семьи, anonymous Auth/удалённый аккаунт,
очистка профиля, чужие/другие профили, rollback ошибки очистки, сохранность UUID/resolve/undo,
закрытые privileged paths. HTTP проверяет реальные API-сессии, браузерную очистку неизвестного
запроса и одновременный consume/delete с доказанным ожиданием блокировки.

Это очищает личный контекст **при удалении профиля**, а не весь lifecycle аккаунта. Ещё нужны:
утверждённый процесс legacy ownership; managed Auth/refresh/revoke; весь экспорт Stage3 и CSV;
удаление аккаунта/архива/копий на других устройствах; сроки хранения квитанций и undo-снимков;
backup retention и повтор удалений при restore; проверка старых клиентов и межустройственных копий.
Никакой срок хранения не выдуман и автоматическое уничтожение квитанций не включено.
Общий журнал, покупки и запасы не выдаются за удалённые вместе с профилем. AI остаётся закрытым.

Источники серверного поведения: [Supabase triggers](https://supabase.com/docs/guides/database/postgres/triggers),
[PostgreSQL row locks](https://www.postgresql.org/docs/17/explicit-locking.html#LOCKING-ROWS).

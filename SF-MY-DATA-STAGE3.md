# «Мои данные»: интеграция этапа 3

База: main `8a090f90487d30297f9e5ccc2140ff0466f8c8d5`, с уже выпущенным безопасным Stage2. Stage1/Stage2 повторно не применялись. Отчёт исходного пакета сохранён в `review/SF-MY-DATA-STAGE3-source.md`; SQL из `review/` остаётся исходным кандидатом и не применяется к production.

Экран в настройках показывает и экспортирует подтверждённые собственные профили/замеры, старые замеры аккаунта и собственный архив переписки/выжимок. Общий холодильник и покупки сюда не входят. Каждый JSON/CSV запрашивает новый серверный снимок, без публичных ссылок и постоянного хранения личного снимка в браузере. При ошибке полный экспорт недоступен. CSV экранирует формулы, кавычки, Unicode и переносы строк.

## Серверная граница

Production-миграция `20261103094224_my_data_owner_isolation_20261103.sql` сформирована после проверки реальной схемы, ограничений, политик, прав и Auth sessions. Добавление owner не меняет значения существующих профилей: все прежние owner остаются NULL. Создатель, имя и членство в семье не являются доказательством владения. Чужие и неприсвоенные профили закрыты, включая прямой Data API. Старые клиентские записи в персональные таблицы запрещены: задержавшаяся запись не восстановит удалённые сведения. Создание/редактирование новых профилей пока недоступно.

RLS и узкий RPC проверяют постоянный аккаунт в auth.users и его действующую auth.sessions по session_id подписанного JWT. Чужой session_id, anonymous Auth, завершённая/просроченная сессия не дают доступа. Чувствительный RPC удерживает блокировки аккаунта и сессии; операции одного пользователя сериализованы. SECURITY DEFINER находится в непубличной схеме, с пустым search_path, явными списками полей, без динамического SQL или переданного с клиента actor. Технические таблицы и raw AI-архив не доступны клиентам. service_role остаётся доверенным серверным оператором, не клиентским механизмом авторизации.

## Удаление и 90 дней

Пользователь выбирает профиль/историю замеров/старые замеры аккаунта/AI-архив и вводит УДАЛИТЬ. Перед удалением сервер выдаёт случайный ticket, связанный с actor, областью и целью. Клиент не назначает ticket. Удаление, производные записи и результат фиксируются одной транзакцией. При потере ответа повтор с тем же ticket возвращает исходный результат и не затрагивает добавленные позднее записи. После начала удаления нельзя отменой потерять номер неоднозначной операции; технические метаданные сохраняются в той же вкладке при перезагрузке/выходе, без веса, замеров или переписки.

Срок ticket и квитанции — **90 дней от выдачи**, без продления при повторе. Истёкший либо неизвестный номер всегда получает отказ, включая номер уже очищенной квитанции. Новый запрос требует нового серверного ticket и нового явного подтверждения. Миграция `20261103094234_deletion_receipt_cron_20261103.sql` включает только очистку технических квитанций каждую минуту. Проверка срока не зависит от исправности планировщика; физическая очистка происходит ближайшим успешным запуском. В квитанции только UUID, область, счётчики и время, без содержимого удалённых данных.

## Приёмка и выпуск

Изолированные проверки выполняют именно production-миграцию: PGlite/нативный PostgreSQL 17.6, настоящий PostgREST 16.5 и подпись JWT. Проверяются два члена семьи, другая семья, legacy NULL, прямые таблицы/права, анонимный аккаунт, отзыв сессии, одновременные API-сеансы, rollback после сбоя производного удаления, повтор и очистка старого ticket, скачивание JSON/CSV, потеря ответа/перезагрузка/смена аккаунта. Отдельный закрытый временный harness проверяет настоящий managed Supabase Auth и браузер без подмены Supabase. Он не входит в release tree и никогда не продвигается на рабочий домен; тестовые аккаунты и синтетические записи удаляются после проверки.

Планировщик pg_cron не доступен в локальных PGlite/vanilla PostgreSQL: там проверяется сама функция очистки, а расписание и его фактический успешный запуск проверяются отдельно в Supabase. Исходный nutrition browser fixture включает питание только на loopback для регрессии отложенных экранов. Это не разрешение включить питание.

Production выпускается из проверенного tree после CI, контроля исходных данных по агрегатным хешам и отдельного staging/acceptance. При откате интерфейса серверные ограничения сохраняются: возвращать старые широкие права нельзя.

## Явные ограничения

- Удаление из резервных копий, повторное применение удалений после restore и ранее переданные внешнему AI-провайдеру копии не подтверждены. Интерфейс прямо сообщает это; данная часть не объявляется полной политикой стирания.
- Нет полного экспорта/удаления Auth-аккаунта, редактирования профилей, автоматического присвоения старых профилей или принятого процесса операторской проверки владения.
- Уже скачанный файл/копию на другом устройстве нельзя отозвать. При экспорте доступ проверяется заново; скрытая вкладка очищает снимок и перечитывает его при возвращении.
- Снимок ограничен 5 MiB, большие архивы требуют отдельной пагинации.
- AI, долговременная память, сводки/автоматизации, питание, пилот и рассылки остаются выключены. «Ужин» проходит отдельную последующую интеграцию.
- Защита скомпрометированных паролей остаётся задачей #8, настройка Auth здесь не меняется.

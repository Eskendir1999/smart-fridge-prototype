## 1. Пользовательская цель

За 10–30 секунд пользователь понимает, что уже есть в доме, какое следующее действие имеет смысл, что для планируемой еды надо купить. Не заставляем вести ежедневный складской учёт ради красивой статистики.

Порядок информационных блоков везде: **Есть дома → Приготовить → Купить**. Это **иерархия**, а не обещание, что интеграция ужина завершена.

## 2. Экраны — готовая структура

### Screen A: «Сегодня»

- Header: «Сегодня», выбранная семья, действие «Добавить продукт».
- A1 «Есть дома»: число **подтверждённых** позиций, ближайшие сроки, компактный список 3–4 продуктов. Не прибавлять pending операции к totals. При пустом запасе показать «Пока нет продуктов» + «Добавить первый».
- A2 «Приготовить»: *пока интеграция #5 не завершена* показывать «Идеи блюд — проверка состава ещё недоступна». Не показывать «можно приготовить»/«всё есть» по совпадению названия. После интеграции доступны состояния: «Достаточно», «Докупить» (точные позиции/количество), «Уточнить количество», «Недоступно с исключениями». Никакого автоматического списания.
- A3 «Купить»: подтверждённые ручные покупки отдельно от **расчётной потребности**. Прогноз не означает добавление покупки. Только после сохранения на сервере менять счётчик.
- Desktop >=1024: доминирующий A1 (левый основной поток), справа A2+A3; mobile <768: A1→A2→A3 строго вертикально; tablet 768–1023: единая колонка или 2 колонки при реальной читаемости.

### Screen B: «Продукты»

- Header + строка поиска, фильтр места (Все / Холодильник / Морозилка), сортировка по сроку.
- Список по умолчанию для точного обзора: название, количество с единицей, место, точная/примерная дата, состояние. Не скрывать единицу, не конвертировать шт в г.
- Desktop: по выбору товара открыть panel detail справа, оставив список и фильтры; mobile: полноэкранный detail с возвратом на прежнюю позицию.
- Основное действие «Использовать» (в том числе частично) только через подтверждённый stock_mutate из #4. «Изменить» вторично, «Выбросить» — отдельное рискованное действие. Не создавать новую локальную мутацию.
- Если ответ сервера не получен, показывать **«Нет подтверждения сохранения»**, а не «Ошибка — не сохранено».
- При edit conflict не перезаписывать чужую новую версию: сохранить поля текущей формы, вывести текущий серверный остаток и предложить пересмотреть изменения.

### Screen C: «Добавить продукт» (мобильная форма)

Поля: название (обязательно), количество (положительное число; дробь допустима только для соответствующих единиц), единица (шт/г/кг/мл/л), место (холодильник/морозилка), срок (необязательно; не подставлять выдуманный срок). Граница для дат: пользовательская дата vs «примерно» отдельно, если источник известен.

- Сначала автофокус имени только там, где это не провоцирует неудобное открытие мобильной клавиатуры; всегда явная видимая label.
- Нативные мобильные клавиатуры (text, decimal inputmode), поле количества не уже 120 px, подписи 14+ px, действия >=44×44 CSS px.
- Ошибка рядом с полем + summary в aria-live; программный фокус на первое ошибочное поле; не очищать форму.
- Нижняя кнопка не перекрывает сообщение и клавиатуру; safe-area-inset-bottom, прокручиваемая форма.
- Фото и штрихкод — альтернативные способы заполнить те же поля; результат распознавания должен проходить подтверждение пользователем.
- Запись съеденного блюда — **другая операция**, её здесь нет.

### Screen D: «Покупки»

- Ясно разделить «Нужно купить» (подтверждённые покупки), «Предлагается по меню» (пока только расчёт/preview) и «Куплено».
- «Куплено»/«Перенести в запасы» обновляет оба списка только после подтверждения #4. Пока pending, показывать статус у конкретного товара, не удалять прежнюю строку.
- Ошибка неизвестного исхода — «Не удалось подтвердить результат. Проверьте статус или повторите безопасно»; повтор только прежнего UUID и payload, не новая операция.
- Одинаковые ингредиенты от нескольких рецептов не суммировать вслепую. Reconcile — отдельная задача после dinner integration.

## 3. Формулировки состояния сохранения

| Состояние | Текст | Действие интерфейса |
|---|---|---|
| idle / editing | «Сохранить продукт» | форма доступна |
| validating | «Проверьте название и количество» | подсветка полей, фокус на первом |
| pending | «Сохраняем…» | disable submit; не меняем подтверждённый склад |
| committed receipt | «Сохранено» | обновить подтверждённый список; только теперь можно закрыть форму |
| ambiguous timeout | «Нет подтверждения сохранения» | не очищать поля/UUID; «Проверить / повторить» тем же запросом |
| confirmed rejection | «Не удалось сохранить. Исправьте данные» | редактирование допускается после подтверждённого отказа |
| conflict | «Данные изменились на другом устройстве» | показать актуальную версию, сохранить ввод, не перезаписывать |
| unauthorized | «Доступ к семье изменился» | безопасный выход из записи; не выдавать успех |
| offline | «Нет соединения. Данные не подтверждены» | не выдавать локальную запись за серверную |

**Не реализовывать второй механизм идемпотентности в UX-ветке:** потреблять receipt и existing states PR #4. При потере ответа первичный UUID должен быть восстановим по контракту PR #4; нельзя создать новый по случайному нажатию.

## 4. Дизайн-система для интегратора

- Основной фон #FBF7F2, surface #FFFFFF, основной текст #1F2A24, основной CTA #2F7A4D, акценты нейтральные.
- Обычный текст >=15–16 px, вспомогательный >=13–14 px (проверять contrast >=4.5:1 для обычного текста); заголовки 24–32 px.
- Шрифт с кириллицей и казахскими символами; не полагаться на Fraunces для русского интерфейса.
- Фокус keyboard visible, label/input link, aria-live для статусов, aria-invalid для ошибочных полей, предсказуемый Tab order.
- Анимация появления/подтверждения 120–200 мс; при prefers-reduced-motion — без движения.
- Статус «примерно» рядом с датой, без обманчивой точности.
- Никаких декоративных «сбережено N кг» как главного CTA и никакого красного алерта на обычное «не хватает ингредиента».

## 5. Обязательные проверки перед передачей интегратору

1. 390×844 / 1280×900; без горизонтального переполнения, CTA и ошибки доступны при экранной клавиатуре.
2. Пустой холодильник / 30 позиций / длинное русское название / неизвестная дата / нулевой остаток.
3. Пустая форма; дробное количество; 0; отрицательное; нечисловое; тип шт; все ошибки возле соответствующего поля.
4. double click — только один pending запрос; сохранённый receipt — только один успешный продукт.
5. Потеря ответа после commit — «нет подтверждения», те же UUID/payload, повтор без дубля.
6. Подтверждённый отказ — исправление формы без потери данных.
7. Смена семьи и аккаунта во время pending — не показывать успех прежней семье.
8. Одновременный расход и редактирование — конфликт, сохранение введённого черновика.
9. VoiceOver/TalkBack и клавиатура: имена контролов, читаемый статус, корректный фокус.
10. Неподключённый Dinner Engine: никакого ложного «доступно приготовить» и никакого списания целого блюда.

## 6. Артефакт и этап интеграции

Рядом: [sf-core-flow-preview.html](./sf-core-flow-preview.html) — **интерактивный, но автономный прототип**. Все карточки и названия там — фиктивные данные. Кнопки добавления моделируют ответ сервера, но не вызывают Supabase, не сохраняют реальных записей и не подтверждают работу PR #4.

**Запрещённые изменения в этой ветке:** index.html, dinner/, supabase/, API, production config, пользовательские данные. Этот отдельный draft PR служит для review структуры/копирайта/состояний. Применение в продукте — после согласования с ответственным за интеграцию и проверок реальных API.

**Оставшиеся зависимости:** PR #3 → PR #4 с миграцией/приёмкой → интеграция Dinner Engine #5 и batch consume/undo → отображение реальных доступных блюд и reconciled покупок → проверка в браузере/на устройстве → production-ответственный. Реальный пилот не начинать.

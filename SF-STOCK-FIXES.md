## Подготовлено

Связанный объём: добавление запаса/покупки → перенос покупки в запас → частичный расход/выбрасывание или редактирование → отмена последнего действия.

- Интерфейс показывает «Сохраняем…», подтверждённое «Сохранено» или ошибку. Списки и статистика меняются только после ответа базы. До отправки UUID и точный запрос сохраняются в localStorage отдельно для пользователя и семьи; повтор после ошибки/перезагрузки использует тот же запрос. Новая запись блокируется, пока результат старой неизвестен. Без доступного localStorage запрос не отправляется.
- `stock_mutate` выполняет покупку одной транзакцией: INSERT запаса + DELETE покупки + квитанция. Повтор UUID не повторяет изменения. Две покупки одной позиции с разных устройств создают одну позицию запаса.
- Расход проверяет ожидаемый остаток/единицу и блокирует строку. Продукт, food_events и food_stats меняются атомарно. 200 г из 500 г оставляет 300 г; нулевые, отрицательные, нечисловые и превышающие остаток значения отклоняются.
- Редактирование также использует UUID, серверную транзакцию и отмену. Исходное состояние фиксируется при открытии формы, включая название, количество, единицу, место и дату. Старая форма не перезаписывает чужое списание или переименование даже после фоновой перезагрузки списка. При конфликте ввод остаётся, а после явного обновления показывается актуальный остаток. Новые правки, набранные во время сохранения старого запроса, сохраняются в форме.
- Отмена восстанавливает исходные идентификаторы, поля, дату создания, владельца, журнал и статистику. При отмене покупки восстанавливается покупка и убирается созданный запас. При последующем изменении строки отмена отклоняется; повтор UUID отмены безопасен.
- Квитанции закрыты в sf_private с RLS и без клиентских прав на таблицу. Публичная RPC — SECURITY INVOKER, привилегированная реализация находится в закрытой схеме с фиксированным search_path. Проверка членства выполняется до ожидания семейной блокировки и повторно после него с удержанием строки членства до commit. Запрос, ждавший в очереди, не может записать данные прежней семьи после выхода/перехода в другую.
- Неоднозначная сетевая ошибка позволяет только безопасный повтор. Подтверждённый отказ транзакции позволяет обновить данные и исправить ввод. Признак старого отказа сбрасывается на диске перед повтором: потеря нового ответа не разрешает отбросить уже выполненный запрос. Поздний ответ старого аккаунта не меняет интерфейс нового.
- Справочные даты обозначены ≈ и названы примерными; у неизвестного товара дата не выдумывается. Исторические даты без происхождения консервативно помечаются примерными, сами даты сохраняются. Удалённый в #3 случайный fallback товара не возвращён.
- Групповой выбор выполняется по одной позиции; подтверждённые позиции снимаются с выбора, ошибка сохраняет оставшиеся позиции и ввод. Виджет очищает только подтверждённые отметки. Из актуального #3 сохранены блокировка одновременных native sync и защита от повторного планирования синхронизации при её собственной перерисовке.
- Панель состояния находится в потоке страницы/формы и не перекрывает мобильные кнопки. Повтор прежнего добавления не очищает новое название, набранное в форме.

## Проверено

- `npm test`: **86/86 PASS**. SQL-миграция выполняется в настоящем PostgreSQL 18.6 (PGlite 0.5.14). Проверены сбои перед INSERT запаса, перед DELETE покупки и перед квитанцией; неудачная покупка полностью откатывается. Ошибки журнала/статистики откатывают расход, ошибка отмены сохраняет исходное состояние, повтор восстанавливает всё. Покрыты UUID, stale edit, права и частичный выбор.
- `npm run test:browser`: **5 групп PASS**, Chrome 156, 1280×900 и 390×844. Pending сохраняет 500 г, ответ даёт 300 г, отмена возвращает 500 г и исходный журнал. Ошибка не убирает покупку/ввод. Потерянный ответ + перезагрузка не создают дубль. Неизвестный товар не получает выдуманную дату. Нет необработанных ошибок страницы и горизонтального переполнения, кнопки доступны.
- `npm run test:http`: **10 групп PASS**. Нативный PostgreSQL **17.6**, PostgREST **16.5**, фактический установленный Supabase JS SDK. Между браузером/SDK и SQL больше нет заглушки RPC или таблиц. Валидность подписи и срока JWT проверяет PostgREST. Подтверждены две одновременно ожидающие API-сессии в pg_locks до освобождения блокировки, а не просто два последовательных запроса.
- Сборка с синтетическими публичными настройками, синтаксис JS и `git diff --check`: PASS.

HTTP-группы:

1. Поддельный/истёкший JWT и anon отклоняются; чужая семья не читает существующие строки; закрытая схема недоступна API.
2. Одновременный повтор одного UUID переносит покупку один раз.
3. Участник сменил семью, пока его запрос ждал блокировку: старый запрос отклоняется, записи нет.
4. Два участника покупают одну позицию: один успех, один конфликт, одна новая позиция.
5. Два одновременных расхода по исходным 500 г: один успех, один конфликт, остаток 300 г.
6. Редактирование и расход конкурируют: проигравший не перезаписывает победителя.
7. Отмена и новый расход конкурируют: остаток и журнал соответствуют одному завершённому исходу.
8. Повтор редактирования и отмена работают через реальный SDK/PostgREST.
9. Мобильный интерфейс: ответ редактирования потерян после commit → перезагрузка → тот же UUID → отмена, без повторной записи.
10. Старая форма после чужого расхода и фонового refresh отклоняется; ввод сохраняется, после обновления видны 300 г; исправление до 250 г и отмена возвращают 300 г, не теряя чужой расход.

Результаты и скриншоты сохранены в папке результатов задачи. CI выполняет все три набора и сохраняет evidence artifact.

## Воспроизведение

```sh
npm ci
npm test
SUPABASE_URL=https://fixture.supabase.test SUPABASE_ANON_KEY=sb_publishable_fixture npm run build
npx playwright install chromium
npm run test:browser
```

HTTP-приёмка требует **пустой одноразовой локальной** PostgreSQL-базы и бинарника PostgREST 16.5:

```sh
SF_TEST_DATABASE_URL=postgresql://TEST_USER:TEST_PASSWORD@127.0.0.1:5432/sf_stock_test_local \
SF_TEST_POSTGREST_BIN=/absolute/path/to/postgrest \
npm run test:http
```

Тест создаёт роли и схему. Он откажется подключаться к удалённому хосту или базе без префикса `sf_stock_test_`. Не использовать существующую базу. CI поднимает отдельный PostgreSQL 17.6 service; локально использовался временный cluster из embedded-postgres 17.6.0-beta.15, после теста остановленный и удалённый. Для нестандартного Chrome есть CHROME_PATH; на macOS используется установленный Chrome, иначе Chromium Playwright. На macOS при необходимости можно задать SF_TEST_POSTGREST_LIBRARY_PATH к совместимой libpq; на Linux CI использует static binary с проверкой SHA256.

## Не выпущено и ограничения

- PR остаётся черновиком. Рабочая база/данные/настройки, production, рассылки и ветка PR #3 не изменялись. Никакие PR не сливались.
- Миграция только подготовлена CLI и проверена изолированно. Она требует существующие schema + household/security + food-log миграции; это не полный bootstrap базы. Уже подготовленный файл уточнён, поскольку он нигде не выпускался. До production — отдельная приёмка копии схемы, pg_advisors и согласованный выпуск миграции/клиента.
- HTTP/JWT/SQL/SDK и несколько серверных подключений теперь проверены по-настоящему. **Выдача токенов и GET /auth/v1/user в браузерном HTTP-тесте остаются изолированными fixtures.** Управляемый Supabase Auth (регистрация, refresh/revoke), шлюз Supabase, фактические настройки проекта и физический iPhone ещё не проверены. Тесты не используют реальные аккаунты или рабочие ключи.
- Supabase-проект проверен только на наличие тестовой ветки: её нет. Платная ветка или новый облачный проект не создавались. Рабочий проект не использовался для тестовых записей.
- Старые production-клиенты продолжают выполнять раздельные запросы, пока не обновлены. Новые гарантии относятся к новой RPC и клиенту; нужен согласованный выпуск.
- Отмена — последнего действия на устройстве в данной семье. Сервер хранит квитанции без очистки ради безопасного повтора. Группа продуктов не является одной общей транзакцией; группового redo нет.
- Очистка данных сайта удаляет локальный UUID неподтверждённого запроса. Объединение одинаковых товаров, фоновая offline-очередь, полный realtime-sync и долговременная история всех отмен вне объёма.
- Справочные сроки и масса штучных продуктов в статистике остаются приблизительными. `npm audit` сообщает три high в существующей цепочке apn → jsonwebtoken/node-forge; обновление APNs относится к отдельной задаче.

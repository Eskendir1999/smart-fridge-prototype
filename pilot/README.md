# SF — минимальная аналитика пилота

Реализация контракта 1.2, 03.11.2026. Это **отдельные модули браузерного учёта и проверенных офлайн-выгрузок**, не включённый сбор данных в приложении. Никаких сетевых запросов, storage, cookies, фоновых таймеров или платежей. Общие файлы приложения и SQL не изменены. Production выпускает только чат `01a19c2c-63f3-7e33-ba82-077718d2bb1f`.

## Что работает

- Строгая структура девяти типов событий; лишние поля, личный текст, вес, неверные enum/числа отклоняются.
- Идемпотентность event_id; другое тело с прежним ID — ошибка. Повтор операции не создаёт второй ужин.
- Разделение факта готовки (M2) и подтверждённого полного цикла (M5). Нужны начало, первый результат, самоотчёт, committed batch и readback; отмена снимает завершение.
- M1–M7 по исходным пяти домохозяйствам. Пропуски обозначаются null, а не нулями; выбывшие остаются в знаменателе.
- M1 считается по первой попытке, независимо от более поздних пропусков. Setup включён в первый результат и чистый баланс. M3/M6 требуют десять подтверждённых дней; базовая линия — минимум два домашних ужина.
- Сверка остатков требует по 3 app→shelf и 2 shelf→app на D7/D13. Ложное «достаточно» отдельно поднимает reliability_alert.
- Ответ о цене не становится платежом. Положительный ответ сверяется с вычисленным балансом времени.
- Опциональный буфер в памяти включается только при enabled + consent + pilotApproved. Он принимает только client-события, отдаёт копию, имеет лимит и очищается при revoke. Это Node API, не подключённый браузерный компонент.

## Источники доверия и ограничения

`serverEvidenceVerified` и `timeEvidenceVerified` — отметки исследователя после проверки происхождения выгрузки и неперекрытия интервалов, **не клиентские разрешения**. По умолчанию false: M5 и временные критерии не признаются доказанными. Этот модуль не проверяет JWT и не предназначен для публичного API. Не передавать эти флаги из браузера участника. В итоговом отчёте всегда `pilot_admission=NOT_EVALUATED` и `payment_permission=false`: численные результаты не закрывают G1–G8 и не разрешают деньги.

Поля source/household_code/operation_id должны быть назначены либо проверены доверенным сборщиком. Строка source=server сама по себе не доказывает серверный commit. Для использования результата необходимы реальные квитанции batch на стороне БД; одиночный `stock_mutate` не подменяет consume_batch.

Данные должны быть нормализованы: одна окончательная запись дневника на день, одна проверка check_id, один ответ цены. Исправления делаются с audit trail до экспорта; конфликтующие дубли отклоняются. Seq задаёт доверенный порядок внутри попытки; одинаковые seq и события до начала отклоняются. Попытка через полночь требует явного разбора и нормализации; модуль её не объединяет молча.

Все интервалы decision/setup привязаны к попытке. Ежедневное maintenance/research/extra_trip допускает attempt_id=null. Общий семейный труд считают в человеко-минутах; одно и то же действие на двух устройствах не должно записываться дважды. Исходные интервалы для проверки пересечений хранятся отдельно с ограниченным доступом; в исследовательском наборе только длительности. Анализатор не может восстановить пересечения из сумм, поэтому timeEvidenceVerified по умолчанию выключен. Успех без времени — не нулевое время.

Значения SYNTHETIC допустимы только для тестовых наборов. Перед живым сбором серверная реализация должна запретить такой build_sha. Не смешивать синтетику с наблюдениями. Один файл — одна пилотная когорта. Входные ID должны быть псевдонимами, а не именами или email; pattern не является механизмом анонимизации.

## Подключение: остаётся сделать в существующей интеграционной работе

1. Подключить opt-in интерфейс и сервис событий после технической проверки на синтетике; живой сбор разрешать только **после G1–G8**. Браузерный модуль и серверная предметная логика уже есть; UI/build, HTTP endpoint и постоянное хранилище пока не подключены.
2. Доверенный сервер выводит source/семью из сессии, проверяет operation_id и scope, дедуплицирует запись. Чужие события не принимаются.
3. Выдавать consume_batch/readback после общей транзакции блюда. Интеграция #5 и batch ещё не закрываются этим модулем.
4. Реализовать разграничение доступа, сроки хранения, удаление и отзыв согласия на сервере, включая технические журналы. revoke() очищает только этот буфер, не сервер.
5. Проверить G7 целиком на синтетическом E2E: UI → сервер → экспорт → этот расчёт, без реальных участников.
6. Согласовать конкретные контакты и канал набора после допуска. Пользователь разрешил работу по пяти направлениям; пилот условно разрешён после G1–G8. Платежи, платные ресурсы и изменение тарифов не разрешены этим пакетом.

Не внедрять данную работу в текущий stock-v1 production-выпуск попутно. Отдельный draft PR позволяет принять код без изменения поведения существующего приложения.

## Браузерный этап

`contract.js` — один валидатор для Node и browser global, `client.js` — компонент в памяти. Проверены 41 unit/VM-сценарий (29 аналитики и 12 клиента). VM-тесты проверяют браузерный global и visibility lifecycle без Node/network/storage; это не Playwright, физический браузер или приёмка приложения.

При будущей интеграции сначала включить оба файла в build и проверить их MIME/CSP, затем загрузить contract.js перед client.js. Ни один script tag в приложении этим PR не добавлен.

```js
const client = SFPilotClient.createClient({
  pilotId: 'pilot-code', householdCode: 'H01', actorCode: 'A',
  buildSha: releaseSha,
  dayIndex: () => currentPilotDay // из локального календаря согласованного пилота
});
// Только после проверки допуска и явного opt-in человека, не из URL-параметра:
client.activate({ enabled: featureFlag, consent: userOptIn, pilotApproved: gatesAccepted });
client.record('attempt_started', {origin:'natural', phase:'product'}, 'attempt-code');
client.startTimer('decision', 'attempt-code');
// ...пользователь выбирает; visibilitychange приостанавливает скрытую вкладку...
client.stopTimer();
client.record('first_result_confirmed', {
  availability:'enough', inventory_checked:true, portions_checked:true,
  list_checked:true, assisted:false
}, 'attempt-code');
const localEvents = client.export(); // только копия; никуда не отправляется
// При отзыве согласия, logout, смене пользователя/семьи:
client.revoke(); // удаляет буфер, таймер и listener; для нового согласия новый объект
```

Нельзя запускать два таймера одновременно у одного actor. Перед результатом нужно явно остановить таймер; событие не получает выдуманное нулевое время. При смене календарного дня stopTimer отклоняет интервал: discardTimer и ручная проверенная оценка. Перезагрузка уничтожает буфер — это пропуск, а не ноль и не гарантированный offline retry. Экспорт нельзя очищать до подтверждённого приёма будущим сервером; текущий компонент вообще не выполняет отправку.

Seq в браузере локален для объекта: доверенный будущий сборщик обязан нормализовать порядок между устройствами, актёрами и серверными квитанциями. Нельзя слепо объединять массивы. Клиент намеренно не создаёт operation_result, stock_readback, day_closed, inventory_audit или price_response. Даже если человек нажал «Приготовлено», это только cooking_reported, не серверный commit. Boolean pilotApproved в браузере не контроль доступа: сервер должен независимо проверять разрешённую когорту и состояние пилота.

При скрытии вкладки таймер ставится на паузу; обычное ожидание сети в открытой вкладке учитывается. Часы monotonic, длительность округляется до ближайшей секунды. Смена scope требует revoke старого объекта; компонент сам не наблюдает Supabase Auth. При буфере 2000 записей запись явно отклоняется, а не вытесняет старые данные. Пример выше не является запуском реального сбора.

## Серверный этап: collector.cjs

Всего теперь **63 локальные проверки PASS**: 29 аналитики, 12 клиента, 22 серверной логики. Это тесты с явными Auth/transaction fixtures; они не подтверждают настоящий Supabase Auth, SQL-адаптер, HTTP transport или RLS. Публичного endpoint в `api/` нет, SQL не добавлен.

`createCollector({authenticate, transaction, now, testMode:false})` предоставляет:

- `ingest(token, {pilot_id, stream_id, events})`: до 100 клиентских событий и 128 KiB за вызов. Не принимает server/manual типы, свободный текст или дополнительные поля. Подтверждённый пользователь, семья, actor, активный пилот, G1–G8, срок допуска и согласие проверяются в транзакции. Допускаются только утверждённые build SHA; SYNTHETIC вне testMode запрещён. Сбор только текущего локального дня пилота, старые буферы требуют ручного разбора.
- `confirmOperation(token, {pilot_id, attempt_id, operation_id})`: читает квитанцию **через доверенный адаптер**, а не из тела запроса. Требует принадлежность семье/попытке, committed consume_batch/undo_batch, все строки применены и подтверждённый readback той же revision. Создаёт два серверных события атомарно. Одиночное списание #4 не считается batch.

Клиент передаёт стабильный stream_id для жизни одного буфера; при повторе отправки его нельзя менять. Пример конверта: `{pilot_id:'SYN', stream_id:'S1', events:client.export()}`. Генерация stream_id и отправка в UI ещё не подключены. Server seq заменяет локальный seq. Повторы сохраняют прежний server seq; коллизия тела с тем же ID отклоняется, а batch откатывается. Локальный seq должен возрастать в потоке. Разные потоки могут иметь одинаковые локальные seq. Префиксы event_id OP-/RB- зарезервированы для серверных доказательств.

После смены дня, потери локального буфера или неоднозначного порядка нельзя автоматически утверждать полную историю: сервис консервативно требует разбор. Текущее владение попыткой закреплено за userId и actorCode. Передача одной попытки другому взрослому пока не поддерживается; это не запрет семейного использования приложения, а граница измеряемого сценария. Внешний сборщик не должен выдавать client-provided source или scope за серверную авторизацию.

### Обязательный контракт постоянного адаптера

`authenticate(token)` проверяет токен реальным провайдером и возвращает `{id}` или отказ. Проверка подписи/срока и состояния пользователя не реализуется самодельным разбором JWT в этом модуле.

`transaction(work)` должен выполнить весь callback атомарно. Все методы ниже асинхронны. Не реализовывать его набором независимых HTTP INSERT/UPDATE: rollback и защита гонок обязательны. Изменения membership, consent и admission должны блокироваться в той же модели транзакций, чтобы отзыв в очереди был замечен после получения блокировки. Метод authorize читает живые значения внутри транзакции, не кэш с момента проверки JWT.

| Метод tx | Обязанность адаптера |
|---|---|
| authorize(userId,pilotId) | Вернуть живой grant: userId, pilotId, householdCode, actorCode, member, pilotActive, gatesAccepted, consent, expiresAt (epoch ms), builds, currentDay. Отсутствие любой гарантии — отказ. Реальные идентификаторы связаны только в закрытом реестре. |
| getStream / saveStream(g,streamId,...) | Ключ `(pilot, household, stream)`; неизменяемые userId/actorCode, lastSeq. Защита конкурентного изменения до commit. |
| getAttempt / createAttempt(g,attemptId,...) | Ключ `(pilot, household, attempt)`; закреплённые userId, actorCode, day. Уникальность, отказ при чужом scope. |
| findEvent / appendEvent(g,...) | Ключ `(pilot, household, event_id)` уникален; digest фиксирует исходное тело+поток. Другая версия тела — конфликт, не UPSERT. Без свободного содержимого и токенов. |
| nextSequence(g) | Монотонный счётчик в пределах pilot+household под блокировкой; общий для client/server. Все записи batch и обновление seq/stream атомарны. |
| readReceipt(g,operationId) | Читать подтверждённый batch из доменной БД; проверить scope и выдать householdCode, attemptId, operationId, status, kind, expectedCount, appliedCount, revision, buildSha. Не формировать квитанцию по клиентскому «готово». |
| verifyReadback(g,receipt) | Доказать commit и соответствие всех затронутых остатков/истории revision; вернуть `{matched, operationId, revision}`. Нельзя сравнить только одну случайную текущую сумму после чужих изменений. |

Не логировать token/полное тело запроса/ошибки провайдера. На будущем HTTP-уровне нужны лимиты запросов, размер до JSON parsing, допустимый origin, обработка Auth и безопасные сообщения об отказе. Пользовательский consent не равен разрешению автоматического research-доступа. Экспорт исследователя, срок хранения и полное удаление с сервера ещё требуют реализации; revoke браузерного буфера не удаляет БД.

### Проверенные сценарии и следующий барьер

В тесте выполнен путь `browser client → transactional fixture → server receipt/readback fixture → offline report`: готовка даёт M2, полное подтверждение — один M5 cycle, отсутствующая базовая линия не создаёт экономию. Проверены подмена scope/source, несовпадающая квитанция, частичный batch, конкурентные повторы, отказ во второй записи с rollback и успешным повтором, отзыв согласия во время ожидания, смена владельца, коллизии ID и серверный порядок.

Следующий этап G7: реализовать **постоянный транзакционный адаптер** вместе с batch-контрактом ужина, затем провести настоящий HTTP/DB E2E на синтетических аккаунтах. После этого подключать компонент в UI/build. Этот PR не даёт разрешения запускать реальные данные и не завершает интеграцию #5.

### Подготовленный транспорт и Supabase Auth

`transport.cjs` экспортирует `createAuthenticator(supabaseClient)` и `createHandler`.
Адаптер передаёт явный bearer token в `auth.getUser(token)`, возвращает только ID,
отклоняет ошибки и анонимные аккаунты. user_metadata не участвует в доступе.
Официальный контракт: https://supabase.com/docs/reference/javascript/auth-getuser
(проверен 03.11.2026; индекс changelog.md недоступен через средство просмотра).
SDK сюда не добавлен: нужно передать серверный клиент существующего приложения
с закреплённой версией, без service_role и без сохранения пользовательской сессии.

Сборка соединяется явно:
```js
const authenticate = createAuthenticator(serverSupabaseClient);
const collector = createCollector({ authenticate, transaction: persistentTransaction });
const handler = createHandler({ collector, origin: appOrigin,
  allowRequest: distributedRateLimiter, enabled: false });
```
Это схема подключения, не готовые реализации persistentTransaction/rateLimiter.
Handler принимает стандартный Request и возвращает Response; предполагаемые пути
POST /pilot/events и POST /pilot/confirm. Он НЕ зарегистрирован в API приложения.
По умолчанию отвечает COLLECTION_DISABLED. Origin проверяется строго, токен только
в Authorization, JSON ограничен 128 KiB по фактическим байтам до разбора; сжатие
отклоняется. Ответы no-store; ошибки не раскрывают детали БД и токены.
Хост должен ограничивать время чтения тела и исполнения, отключить логирование
тел/Authorization и обеспечить распределённый rate limit по доверенным данным
соединения. Origin не заменяет аутентификацию. Проверка getUser не заменяет
проверку актуального членства/согласия внутри транзакции.

Проверка: `node --test tests/pilot-*.test.cjs` — 73/73 на этом этапе.
10 новых тестов используют Request/Response и подменённый Auth SDK/collector;
это не проверка сети Supabase или развёрнутого HTTP-сервера. CI предыдущего
коммита 6b1f6ba — success (run 41594491955). Новый коммит проверяется отдельно.
G7 всё ещё открыт: постоянная БД, настоящий Auth/HTTP E2E, batch ужина, UI,
удаление/экспорт/retention и приёмка всех G1–G8 требуются до реального сбора.

### Постоянное SQL-хранилище — этап 03.11.2026

`postgres.cjs` реализует transaction для collector через переданный node-postgres
Pool. `pilot/sql/storage.sql` — определение частной схемы для review и изолированной
приёмки, не production migration. В рабочей базе не выполнялось.
Одна строка на пилот хранит grants и состояние; SELECT FOR UPDATE сериализует
записи малого пилота. Это сознательное ограничение пяти семей, не универсальная
аналитическая БД. Максимум 10 000 событий, затем отказ без потери старых данных.
Транзакция сохраняет события, попытки, последовательности и streams вместе;
ошибка вызывает ROLLBACK, соединение освобождается (ошибочное уничтожается pool).
Блокировки: https://www.postgresql.org/docs/current/explicit-locking.html

Права PUBLIC отозваны, RLS включён, клиентских политик нет. Привилегированный
backend provisioning ещё не подготовлен; данный код нельзя просто подключить
через anon/REST. Grants заполняются только доверенным серверным процессом.
Перед выпуском нужно связать их с каноническими membership/consent, чтобы изменения
получали тот же lock и не оставляли устаревшее разрешение. Копирование grants без
синхронного отзыва недопустимо. Секреты в файлах не нужны.
readReceipt и verifyReadback обязательны и используют то же соединение; реальные
адаптеры batch ужина пока отсутствуют. Не подменять их успешными заглушками.

Тест pilot-postgres.test.cjs использует имеющийся в репозитории PGlite 0.5.14:
запись на диск → закрытие/открытие → дедупликация, полный rollback пачки,
отзыв согласия, отказ SELECT роли без доступа. Все 74 теста пилота PASS локально.
Это SQL-тест, а не подтверждение сетевого PostgreSQL/Supabase: многосессионные
гонки, сбой COMMIT/сети, backend role/RLS и реальный Auth ещё требуют приёмки.
Сбор событий по-прежнему отключён. Не закрывает G7 или допуск G1–G8.

### Проверка канонического членства

Адаптер postgres теперь требует `householdId` (UUID рабочей семьи) в доверенном
разрешении пилота и сверяет его с `public.household_members.household_id` для
проверенного Auth user ID. UUID хранится только в закрытом разрешении, не в событиях.
Отсутствие строки, несовпадение или отсутствие householdId запрещает запись.
Копия `member` больше не является источником истины. Строка membership читается
`FOR SHARE` на том же соединении до COMMIT: смена household_id не может пройти
незамеченной посередине записи. Порядок блокировок: pilot, затем membership.
Процессы, меняющие обе сущности, должны соблюдать этот порядок; deadlock означает
откат, а не разрешение записи. Согласие пилота остаётся в закрытой строке grants.

Источник формы таблицы: supabase-household-migration.sql и
supabase-household-security-migration.sql в репозитории (прочитаны 03.11.2026).
Не подтверждено применение этих схем в production. Тестовая таблица содержит
только необходимые UUID-поля; это не приёмка настоящего Supabase Auth/RLS.
Серверный CI дополнен гонкой: UPDATE семьи удерживает lock, ingest ждёт,
после COMMIT старое разрешение пилота отклоняется. Backend-права для SELECT
FOR SHARE и работа с рабочей RLS всё ещё требуют отдельной приёмки.
Batch ужина в PR #5 (59d3942) по-прежнему не реализован: receipt/readback не подключены.

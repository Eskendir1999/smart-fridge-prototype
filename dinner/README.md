# Количественный расчёт ужина

При наличии одного совпавшего названия старый `computeCookable()` мог предложить омлет без яиц;
проверка недели не отличала 20 г сыра от запаса на все блюда. `model.js` считает полную потребность,
вычитает распределённые партии из копии недельного плана и возвращает конкретный дефицит или
явную неопределённость. Он не изменяет запасы и не делает запросов к серверу.

Это независимый модуль для дальнейшей интеграции. В `index.html`, сборку и service worker он пока
не подключён. Пользовательский сценарий приложения остаётся прежним. Миграций и новых RPC здесь нет.

## Использование

CommonJS: `require('./dinner/model.js')`; обычный `<script>` создаёт `globalThis.SFDinner`.
Экспортируемые функции одинаковы в обоих окружениях. Современный браузер должен поддерживать BigInt
и structuredClone. Собственных зависимостей у модуля нет.

```js
const { adaptInventory, adaptProfiles, evaluateMenu, suggest, shopping, formatAmount } = SFDinner;
const lots = adaptInventory({
  rows: savedFridgeRows, householdId, confirmed: true,
  aliases: { 'твердый сыр': 'cheese' } // только проверенные полные имена
});
const profiles = adaptProfiles({ rows: savedProfileRows, householdId, profileIds });
const context = { lots, profiles, ingredients, householdId };
const cards = suggest({ ...context, recipes, day: '2026-11-02', portions: 2 });
const menu = evaluateMenu({ ...context, meals: [{
  id: 'dinner-2026-11-02', day: '2026-11-02', portions: 2, recipe: selectedRecipe
}] });
const desiredShopping = shopping(menu);
// formatAmount(190000, 'mass') -> '190 г'
```

Дата передаётся локальным YYYY-MM-DD явно, а не берётся из UTC браузера. Для недели нужно передать
все выбранные приёмы одним `evaluateMenu`, чтобы не засчитать один запас несколько раз. Три карточки
`suggest` — независимые альтернативы на одном снимке, не три одновременно доступных блюда.

## Форматы

- `ingredients`: объект по каноническому id, значения `{ name, tags, allergensReviewed: true }`.
  `tags` — полный список из `dairy, egg, fish, nuts, gluten`, включая составные продукты. Неизвестная
  разметка исключает рецепт. Новые типы ограничений требуют расширения модели и UI, а не игнорирования.
- `Recipe`: `{ id, version, basePortions, ingredients: [{ingredientId, quantity: {value, unit}}],
  allowedModes: ['standard'], ... }`. Версия и базовые порции — положительные целые; количество каждой
  обязательной строки положительно и измеримо. Полная замена — другой рецепт со своими шагами/составом.
  Сам модуль не генерирует и не объявляет подходящими новые варианты.
- `Lot`: `{ id, householdId, ingredientId, quantity: {value, unit, source}, expiresOn, dateSource, version }`.
  quantity.source — `measured/user` для достоверного запаса. `catalog_default/legacy_unknown` и неизвестные
  значения требуют уточнения. `version` переносится в allocations, но модуль не валидирует серверный токен
  и не использует его для записи. Обязательная серверная проверка версии — задача сохранения.
- `Profile`: `{ id, householdId, mode, exclusions }`. Применяются все явно выбранные профили; молчаливого
  переключения на первый профиль/standard нет. Разрешённые режимы — standard/breastfeeding, но каждый рецепт
  должен явно разрешить свой режим. Это проверка каталога, не медицинское заключение.
- Единицы: `g/kg`, `ml/l`, `pcs`. Вход — число либо decimal string, до трёх десятичных знаков. Между массой,
  объёмом и штуками переводов нет. Штуки целые. Ломтики, ложки и упаковки требуют уточнения.
- Расчёт и результат — целые тысячные г/мл/шт плюс обязательная `dimension`. `amount()` возвращает
  `{value, dimension}` либо null. BigInt используется только внутри; результат JSON-совместим.
  Непредставимое масштабирование порций даёт clarify, переполнение агрегата покупок — явную ошибку.
- `evaluateMenu` возвращает `{householdId, profileIds, status, label, lines, blocked, unresolvedLots}`.
  Строки содержат required, knownAllocated, shortfall, missingExact, allocations по lotId/expectedVersion,
  excludedLots и uncertainLots с причинами. Null status означает исключённый рецепт/профиль, а не «всё есть».

`adaptInventory` принимает подтверждённые серверные строки либо UI-форму, **сохранившую householdId**.
Форма `{_id, qtyNum, expiresOn}` без семьи отклоняется: интеграции нужно сохранить контекст из серверного
снимка. Адаптер не читает `defaultQty`, не подставляет срок и не принимает pending/demo данные без явного
подтверждения вызывающей стороны. Флаг `confirmed` сам по себе не доказывает подтверждение базы.

DB-поля: id, household_id, ingredient_id, qty_num, unit, quantity_source, expires_on, date_source,
expiry_estimated, compartment, version. Поддерживаются camelCase аналоги (id → _id).
В существующей схеме PR #4 полей identity/quantity_source/date_source/version ещё недостаточно:
адаптер не создаёт их, источник отсутствующих данных — legacy_unknown. `expiry_estimated: false`
не доказывает дату с упаковки. Explicit null DB-поля не заменяются старыми camelCase значениями.

Просроченные и нулевые партии исключаются, включая морозилку. Дата проверяется на день готовки;
подтверждённая дата, равная ему, допускается в расчёт. Условия хранения и качество не удостоверяются.
Неопознанные потенциально пригодные партии могут покрывать дефицит: до их сопоставления он получает
clarify вместо выдуманной точной покупки. Если известного запаса уже достаточно, лишняя неопределённая
партия не отменяет enough.

## Покупки и ограничения сохранения

`shopping()` выдаёт только точные дефициты разрешённого меню. Известные дефициты других строк остаются
доступны, когда общий статус clarify. Заблокированное меню отклоняется. Это desired demand, не операция
добавления: UI должен сохранять его вклад по scope/revision с заменой предыдущего вклада при перерасчёте.
Повторный вызов не изменяет корзину. Не следует суммировать повторный результат с предыдущим вслепую.

PR #4 (`0faa7f8`) предоставляет подтверждённые одиночные операции, повтор и отмену. По доступному контракту
его групповой выбор выполняется по одной позиции; общего атомарного расхода блюда нет. Здесь нельзя
сделать цикл `stock_mutate('used')` и объявить блюдо сохранённым: ошибка второй строки оставит первую
списанной, а отмена на устройстве покрывает последнее отдельное действие.

Для завершения нужны: атомарный batch consume/undo; постоянная identity/provenance партии; проверка
семьи, профиля и свежего снимка перед подтверждением; стабильный id операции при потере ответа;
подключение одного расчёта к Home/рецептам/меню и сохранение выбранных порций/замены. Текущая адаптация
семьи — клиентская фильтрация, **не** замена RLS/серверной авторизации.

## Проверки

```sh
node --test tests/dinner-model.test.cjs
node --check dinner/model.js
git diff --check
```

27 тестов: омлет без яиц, 20 г сыра на неделю, порции, полная замена, несколько профилей, FEFO,
истёкшие/примерные даты, неизвестные количества/имена, несовместимые единицы, точность/переполнение,
DB/UI-адаптеры, null/provenance, сохранность снимка, детерминированность и сохранение количества на
45 вариантах недельного плана. CommonJS и браузерный global API проверены одним кодом через VM.

`tests/fixtures/dinner-catalog.json` — четыре тестовых рецепта; не выпускной каталог. Продукты/количества
и режимы требуют отдельной проверки перед подключением. Полноценные browser E2E, Auth/HTTP/RLS,
многосессионный расход, реальная корзина и отмена этим набором не проверяются.

Общие файлы index.html, package.json/lock, build.js, sw.js и SQL PR #3/#4 не изменены. Черновой PR этой
части может рассматриваться независимо; его наличие не означает завершение пользовательского пути.
